# Natural-language baseline

`myr_runner::prose` is the comparison pipeline required by the benchmark
(specification, "Conditions" and Week 3, day 1). It runs the same prepared
mission as MW/0 with a different inter-agent protocol: agents address prose
messages to later stages instead of exchanging MW/0 objects.

```text
myr run myr.yaml --config runtime.json --repository path/to/repository --root path/to/new-run --pipeline prose
```

Like `myr run` for MW/0, this executes the configured providers and consumes
subscription quota or API billing. There is no backend fallback.

## What both pipelines share

Both pipelines use one `setup::prepare` result: the repository snapshot, the four
sealed role providers (planner, worker, two reviewers of different lineages),
the writable prefixes and protected paths, the command verifier policies and
their Docker sandbox, and the call, reference-token and time budgets.

- **Budgets.** One dispatcher per mission with the sealed limits. Each stage
  also has a local budget with the same limits, as an MW/0 TASK does. Calls
  are journaled in the private audit store exactly as for MW/0.
- **Acceptance commands.** `seal_acceptance` compiles a runtime-owned seal
  whose only criteria are the mission's required verifiers. These are positive
  binding `core.command_succeeds` ATOMs, bound to the mission by the same rule
  that binds a planner proposal. Agents never see this seal. It exists so the
  baseline candidate goes through the same reconstruction, sandbox execution
  and command-evidence recording as an MW/0 candidate.
- **Candidate.** Worker `write_file` actions become runtime-created full
  replacement DELTAs for existing baseline paths. `candidate::prepare_recorded`
  then reconstructs the candidate under the same write prefixes and protections.
  As in MW/0, a worker cannot create new paths.
- **Repairs.** Malformed or semantically invalid actions allow two repairs, and
  a third ends the stage with `INVALID_AGENT_OUTPUT`. Capability violations
  fail at once with `CAPABILITY_DENIED`. Rejected raw output is quarantined.
- **Shared tools.** `fetch`, `fetch_many`, `put_artifact` and `finish` use
  declarations generated by the same function as the MW/0 schema, so they are
  byte-identical. Fetched artifacts use the same `render_artifact` rule in both
  pipelines, and both use the same multi-action envelope with `@k` references
  to objects created earlier in the same response.

## Frozen context policy

Each agent receives the mission, its role instruction, the messages explicitly
addressed to it, and its own tool outputs. There is no global thread, no
automatic summary, and no access to another agent's conversation.

| Stage | Initial context | May address |
| --- | --- | --- |
| Planner | mission, instruction, repository listing | worker, reviewer_a, reviewer_b |
| Worker | mission, instruction and write policy, planner messages to it, repository listing | reviewer_a, reviewer_b |
| Reviewer A/B | mission, instruction, messages to that reviewer, baseline/candidate listing with changed paths | nobody |

Each message becomes one `INTER_AGENT_PROSE` segment, `Message from <sender>:`
followed by the text. The label is protocol-injected, so it is counted too.
Messages repeat on every later call of the recipient, just as repeated MW/0
context is counted on every call. Messages can only go to later stages in the
fixed order, and a message with no valid recipient is a repairable error.

Segment classes follow Appendix C.1 as revised, classifying artifact content
by provenance rather than by retrieval channel:

| Content | Class | Counted |
| --- | --- | --- |
| Mission and role instructions | `GOAL` | No |
| Initial repository listing and files, however fetched | `DIRECT_REPO` | No |
| Tool receipts, the agent's own artifacts, repair feedback | `LOCAL_TOOL` | No |
| Addressed messages | `INTER_AGENT_PROSE` | Yes |
| Files written by another agent, the reviewer's candidate listing | `INTER_AGENT_ARTIFACT` | Yes |
| Response schema (all baseline declarations are shared) | `SYSTEM` | No |

A baseline reviewer reading the worker's file therefore pays the same cost as
an MW/0 reviewer fetching it through CAS. The baseline records no CAS retrieval
traffic.

## Source pass (primary condition)

With `--source-view <dir>`, the planner is the source agent in two passes, as
the same planner slot in both pipelines:

1. It plans from `worker_view`, and its plan messages are queued.
2. The plan is frozen.
3. A fresh source-pass context holds the mission, the fixed source
   instruction and a listing of the private `source_view`. The pass reads only
   those files, served from memory, and never the shared baseline.

Its only output channel is the protocol under test: prose messages here, and
CLAIM/ATTEST, assumption proposals and artifacts in MW/0. Those MW/0 outputs are
added to the worker's and reviewers' TASK inputs. The source TASK has no write
capability or obligations.

Republishing a private-only file byte for byte is a repairable rejection; the
source must quote the relevant text instead. After the run, each report records
`source_blobs_absent`, confirming that no private-only blob reached shared CAS.
A `false` value prevents delivery.

## Reviewer visibility (revision 2)

Baseline reviewers see source prose only when it is addressed to them, and a
single REJECT prevents delivery. MW/0 reviewers see, and must review, every
non-HEURISTIC CLAIM the worker received. A contradicted, unpromoted received
CLAIM blocks MW/0 delivery. The difference is declared in the specification as
a property of the protocol under test.

## Baseline-only tools

| Tool | Roles | Effect |
| --- | --- | --- |
| `send_message(to, text)` | planner, worker | Queue prose for later stages; bounded to 512 KiB |
| `write_file(path, content_ref)` | worker | Set an existing writable path to an own artifact or repository file; a later write to the same path replaces the earlier one |
| `submit_review(verdict, message)` | reviewers | One final `APPROVE` or `REJECT` with an explanation that no agent receives |

## Outcome

The pipeline order is planner, worker, the sealed command verifiers on the
candidate, then reviewer A and reviewer B. If the planner or worker stage does
not finish, the mission stops at PARTIAL. The report
(`myr-prose-pipeline-v0`) is COMPLETE and `delivered` only when all of the
following hold:

- all four stages finished and no FAIL was recorded;
- every required verifier supported its criterion;
- both reviewers submitted `APPROVE`;
- the mission deadline held.

Otherwise the state is PARTIAL and nothing is delivered. The baseline has no
assumption registry, so it never reports COMPLETE_WITH_ASSUMPTIONS. It also
never reports UNSAT. The MW/0 mechanical UNSAT proof applies only when no
baseline path is editable, and no benchmark case should be built that way.

The report retains stages, messages, reviews, command verifications, failures,
the budget ledger, reference accounting totals and the last dispatch
checkpoint. An immutable copy goes to the private audit store. MW/0 reports now
carry the same `accounting` totals.

## Effect on MW/0 accounting

MW/0 dispatch now passes `schema::prose_shared_schema()`, the union of every
baseline declaration, as its shared schema. The four common declarations are
therefore `SYSTEM` in both pipelines. Every other MW/0 declaration (`emit_*`,
`review_claim` and the catalog-restricted planner actions) stays
`PROTOCOL_SCHEMA` on every call. Before this change the comparison set was
empty, and the MW/0 pipeline was charged for the shared tools as well.

## Evidence and open points

The tests inject provider responses and synthetic command receipts. They cover:

- a complete, delivered run with exact communication token and byte totals;
- per-recipient message isolation;
- no delivery after a reviewer rejection or a failing verifier;
- immediate capability denial and repair exhaustion;
- a missing verdict and call-budget exhaustion;
- refusal of an acceptance seal that does not match the mission;
- a source pass that reads the private view only after planning, has a verbatim
  republication refused, and transfers only prose, with no private blob in
  shared CAS;
- exact provenance accounting, where the candidate listing and the
  worker-authored file read by a reviewer count and repository reads do not.

A CLI test runs `--pipeline prose` offline with absent provider executables. It
records PARTIAL with one attempted planner call and no fallback. None of these
tests is live-provider evidence.

Still open:

- **`view_diff`.** The CLI does not check the source view against the declared
  `view_diff`. That belongs to corpus admission.
- **Pilot and freeze.** The instructions, context policy and schema must still
  be checked in the pilot and frozen in the official manifest.
